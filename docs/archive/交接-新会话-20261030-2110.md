## 4. 已解决的问题与仍存在的问题

已解决（有实机证据）：

1. **PDR `tms/servreg -6` 与基带无关**（modem9）。pmic_glink 先问到用户空间 mapper（jsn 只有 adsp audio/sensor/root），查 `msm/adsp/charger_pd` 得 -ENXIO；11 ms 后问内核 qcom_pd_mapper（6 项，含 `msm/modem/root_pd` 180）匹配成功。#207 无基带也出现同一 -6。两个 mapper 都保留未动。
2. **崩溃恢复时 modem_dtb PAS -12**（modem9 定位、modem10 修复）：`qcom_scm` `dma_alloc_coherent` 4044 字节返回 NULL。原因是所有保存配置都关了 ZONE_DMA/ZONE_DMA32（`CONFIG_EXPERT=y` 下可关），约 9.9 GiB 内存在 4 GiB 以上，32 位 coherent 掩码无低端区可退。打开两项后 3 次崩溃全部恢复到 running。
3. **IPA `ipa_ipfltri_sys_mem_init` 45056 字节 SMEM 断言**（modem11）：Linux 在 0.635 s 先分配了 SMEM item 497（0xb000），与基带自己分配冲突。不预分配后断言消失。
4. **IPA 访问 IMEM 引发 SMMU fault + BAD_SNOC_ACCESS**（modem12）：modem11 fault iova 0x146a9080；主线 sm8550.dtsi 的 modem-tables 在 0x14688000，厂商是 0x146a8000。改地址后首次启动 4584 s 内 0 崩溃。
5. **ModemManager reprobe 循环**：卡槽补丁（用户态）解决，见第 3 节。
6. 同一次开机内 stop/start rmtfs 无法重试基带（rproc power 引用不归零）：已知限制，每次试验需重启。

仍存在：

1. **modem12 第二次启动（20:34，boot_id `57a575e2`）在 1043.6 s 出现 SMMU context fault**：`iova=0x81dfbf00, fsynr=0x90001, cbfrsynra=0x4a0, cb=6`，紧接 `ipa: unexpected tagged packet from endpoint 15`；1047.2 s 基带报 `ipa_hal.c:2919 IPA Assert ... Received FATAL IPA IRQ`。之后每次恢复都在约 61 s 后 `error -110 awaiting init driver response`，紧接同样的 FATAL IRQ，到 1326 s 共 12 次。日志 `work/claude-logs/modem12b-57a575e2/{dmesg,journal}.log`、`modem12b-crash-20261030-2057.log`。
   - **iova 0x81dfbf00 落在 SMEM 保留区 0x81d00000–0x81efffff 内**（dmesg `smem@81d00000`，厂商 `smem_region@81d00000`）。SID 0x4a0 是 IPA AP 上下文。modem11/12 跳过了 `ipa_smem_init()`，于是 SMEM 497 没有映射进 IPA 的 IOMMU 域，而基带自己分配的 item 497 很可能在这段地址。**这是当前最强假设，未验证**：基带让 IPA 硬件访问它自己分配的 SMEM 过滤表，AP 侧 SMMU 没有该映射。
   - 厂商 ipa_smmu_ap：`qcom,ipa-q6-smem-size = <0xb000>`、`qcom,additional-mapping = <0x146a8000 0x146a8000 0x2000>`、`qcom,iommu-dma-addr-pool = <0x20000000 0x20000000>`、`qcom,use-64-bit-dma-mask`（`work/device-info/fuxi-live.dts` 约 29475 行）。
   - 第一次 modem12 启动（`0255c5ab`）4584 s 无此 fault，说明触发与时机/流量有关（此时刚做过 usage preference 切换和飞行模式切换，注册在 5G NR）。
2. **注册不稳定**：第一次启动注册 CHN-UNICOM 460-01 LTE 后 15 s detach，无 Network Reject（reject_info_valid=no）。第二次启动（不跑 MM，直接 qmicli，日志 `modem12b-qmi-nomm-20261030.log`）：137–415 s 注册与 searching 交替；在 voice-centric 下 IMSA 返回 InvalidOperation（IMS 未运行）；改 data-centric（usage 1→2）后 445–761 s 一直 not-registered；切一次飞行模式后 771 s 起连续注册约 170 s；随后 1043.6 s 出现上面的 SMMU fault。崩溃重启后 usage 回到 1。
3. 恢复循环里 `-110 awaiting init driver response`：恢复后 AP 侧 IPA 没有完成 INIT_MODEM_DRIVER 交互。
4. ModemManager "Failed to find a net port"：modem12 下 `rmnet_ipa0` 已创建，但系统 MM 未打补丁，数据连接未测成。
5. 用户报告的 Android 偶发进不去、长时间黑屏、Linux 启动暂黑屏需按电源键：用户要求暂缓，不插队。

## 5. 已尝试但失败或被排除的方案

- 同次开机内 `systemctl restart rmtfs` 或 stop/start 重试基带：不可靠，必须整机重启。
- 用户空间 pd-mapper 作为修复：装上后故障依旧；PDR -6 已证明与基带无关。**不要禁用任何一个 mapper。**
- data-centric usage preference 解决 detach：未成立（见第 4 节第 2 条）。
- `scripts/fuxi-test-recovery.sh` 用来探测连接：不行，它会重启并写 recovery_b，而且不会自动恢复 #207。
- UFS HS-G5（`work/patches/pending/ufs-qcom-sm8550-g5.patch`）：G5 下 `reboot -f` 让手机进了 EDL，已搁置。
- modem11 nosmem 被当作最终修复：不成立。它消除了 SMEM 断言，但 SMEM 497 没有映射进 IPA SMMU，很可能就是 modem12 第二次启动 fault 的原因（未验证）。
