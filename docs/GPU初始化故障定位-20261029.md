# Adreno 740 GPU 初始化故障定位（2026-10-29）

## 结论（20:00 CST 更新：已修复）

根因是 **ZAP 固件签名不对**，内核、设备树和 PAS 路径都没有问题。早先从 Android `/vendor/firmware` 提取的
`a740_zap.mdt`/`.b02` 是高通 SecTools “General Use Test Key (for testing only)” 测试密钥签名（证书 2025-11-28），
量产 TZ 拒绝 → `qcom_pas_init_image` 返回 `-22`，随后 GMU `GPU_SET` OOB 超时。
Android kgsl 实际请求 `a740_zap.mbn`，由 ueventd 在 **`/odm/firmware`** 找到；`/odm/firmware/a740_zap.mdt`
为 “General Use for Xiaomi Secureboot” 签名（与 ADSP/modem 固件同一证书链）。两版 b00/b01 逐字节相同，只有 mdt/b02 不同。

修复：把 `/odm/firmware/a740_zap.{mdt,b00,b01,b02}` 部署到 Linux `/lib/firmware/qcom/sm8550/xiaomi/fuxi/`
（文件名不变，DT `firmware-name` 不改，未重编内核）。原测试签名文件备份在手机 `/root/fw-backup-20261029-zap/`，
小米签名版及设备端哈希在 `work/backup/gpu-zap-odm-20261029/`。

实测（screen-audio9 / `#187`，boot `c2cfcb97-…`，`reboot recovery` 干净重启后）：
- dmesg 不再有 zap `-22`、`gpu hw init failed`、GMU OOB 超时；debugfs `gpu-initialized: 1`；
- Mesa 26.2.4 freedreno：`OpenGL core profile renderer: FD740`，OpenGL 4.6；
- phoc 去掉 `WLR_RENDERER=pixman` 后加载 libgallium 并打开 renderD128，Phosh NRestarts=0；
- 用户现场确认“明显流畅了”（此前 Pixman 软件合成时 phoc 吃满单核，用户反馈延迟+掉帧）；
- 交互后无 GPU hang/fault/recover，DPU underrun 0，devfreq 220–680 MHz，最高约 39°C。
日志：`work/claude-logs/gpu-zap-fix-20261029.log`。

仍待处理：`msm_devfreq_init: Couldn't register GPU cooling device`（GPU 没有接入温控 cooling 设备，
重负载下仅靠 tsens/LMh 硬件保护）；长时间 GPU 负载、温度与熄屏/唤醒后 GPU 恢复尚未验收。

部署脚本已同步：`scripts/fuxi-m6-display.sh` 的 ZAP 只从 `/odm/firmware` 取并拒绝测试签名；
`scripts/fuxi-m5-phosh.sh` 改为 Mesa 渲染器确为 FD7xx 才启用 GPU，否则仍回落 Pixman。

## 历史记录（修复前的定位过程）

### 当时结论

screen-audio8 的 DSI 面板与显示 modeset 可以独立工作；Phosh 使用 Pixman 软件渲染。Adreno GPU 加速没有通过验收。启动日志表明两个非安全固件文件已找到并加载，但签名 ZAP 在 Qualcomm Peripheral Authentication Service（PAS）初始化处返回 `-22`，随后 GMU 的 `GPU_SET` OOB 请求超时。此错误与 DSI connector、面板初始化及画质不能混为一谈。

## 证据

`work/claude-logs/rtest-20261029-140912/ssh.txt` 记录：

- `qcom/a740_sqe.fw` 从新固件目录加载；
- `qcom/gmu_gen70200.bin` 从新固件目录加载，GMU 报告版本 `v4.1.9`；
- `qcom/sm8550/xiaomi/fuxi/a740_zap.mdt` 初始化返回 `-22`，重试仍失败；
- 随后 `a6xx_gmu_set_oob` 报等待 `GPU_SET` 超时。

相同设备提取的 ZAP 固件保存在 `work/backup/display-install-20261029-104150/gpu-firmware/`，来源与各文件哈希记录于 `manifest.json`。`.mdt` 与 `.b00`、`.b01`、`.b02` 文件均存在，固件路径缺失不能解释本次 `-22`。Linux 内核中 `drivers/gpu/drm/msm/adreno/adreno_gpu.c` 先取得固件和安全内存区域，再调用 `qcom_mdt_load()`；错误日志来自 `drivers/soc/qcom/mdt_loader.c` 的 PAS image initialization 返回路径。当前源码与构建配置启用了 `CONFIG_QCOM_PAS` 和 `CONFIG_QCOM_MDT_LOADER`。

## 还不能断定的部分

现有日志无法区分设备专属签名/元数据是否被当前 Secure World 接受、PAS 固件状态是否满足初始化条件、保留内存/平台依赖是否正确，或是否存在其他安全固件兼容问题。当前没有证据支持修改显示时序、替换 ZAP blob、绕过认证或关闭安全检查。不要把屏幕工作归功于 GPU：桌面目前走软件渲染。
