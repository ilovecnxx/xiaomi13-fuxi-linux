# 小米 13 `fuxi` 原生 Linux 移植评估

| 项目 | 内容 |
|---|---|
| 评估日期 | 2026-10-24 |
| 设备 | Xiaomi 13 `fuxi` / SM8550 |
| 系统基线 | LineageOS 24.0 / Android 17 / kernel 5.15.211 GKI |
| 启动状态 | bootloader 已解锁；ABL 已实测接受自定义镜像的 `fastboot boot` |
| 当前路线 | 纯主线 Linux 内核 + fuxi DTS + 主线驱动 + 内置 initramfs |
| 目标 | 先在不写分区的前提下启动内核并拿到 USB shell，再逐项补设备支持 |

## 路线边界

本项目只做纯主线 Linux：不使用 Android vendor kernel、Halium、Droidian、libhybris 或 Android HAL。edk2 UEFI 只用于验证启动链和辅助调试，不作为最终系统的存储引导器。

## 结论

原生启动的第一阶段是可做的，但目标必须拆开：先证明内核和 initramfs 能运行，再解决存储、显示和手机外设。edk2 已证明 ABL 的临时启动链路可用；DEBUG edk2 还能进入 GUI、触摸可用，但当前 edk2-msm 的 SM8550 平台没有配套 UFS、时钟和 PHY DXE，UEFI 看不到手机内部存储。因此项目主线改为绕过 UEFI 存储栈，直接用 `fastboot boot` 加载 Linux 内核。

这条路线的第一个实测目标不是 Ubuntu 桌面，而是内核日志和 USB CDC ACM shell。只有这个闭环成功，后续 UFS 和图形工作才有可靠的调试入口。

## 当前实现

`scripts/native-kernel-build.sh` 会完成以下工作：

- 从 `build/fuxi-min.dts` 生成 fuxi DTB，并加入内核 DTS Makefile。
- 开启 SM8550 基础栈、RPMh regulator、interconnect、IOMMU、USB DWC3、USB2 PHY、USB gadget serial、devtmpfs 和 initramfs。
- 将地址空间切换到 48-bit，关闭旧配置中的 LPA2，减少在手机上启动时的兼容变量。
- 把 `build/initramfs/` 内置进内核。init 会挂载 proc/sysfs/devtmpfs/devpts，写入 `FUXI_NATIVE_INIT_OK`，等待 `/dev/ttyGS0` 并提供交互 shell。
- 用 Android boot header v2 生成 `build/native/boot-fuxi-mainline-test.img`；脚本不会调用 adb/fastboot。

## 重新整理后的阻塞点

### P0：必须先解决，才能判定内核是否真正启动

1. **内核 handoff 后早期启动**：v2（带压缩 ramdisk）和 v4 测试镜像都已被 ABL 接受并发送，但 handoff 后返回 fastboot。当前优先级高于继续调整 header 版本。
2. **内存与 DTB 可信度**：最小 DTS 使用从厂商 DTB 提取的内存区间，仍需通过早期串口或 USB 日志确认没有内存映射错误。任何内核早期 external abort 都先归到 DTB/地址布局检查。
3. **USB gadget 闭环**：当前只启用 USB2 peripheral，依赖 DWC3、QCOM glue、eUSB2 PHY、UDC 和 `USB_G_SERIAL` 同时成功 probe。主机未出现 CDC ACM 前，不能把“没有 shell”判断为 initramfs 失败。

### P1：内核启动后最先处理

1. **UFS 内核节点**：主线有 `ufs-qcom` 和 SM8550 PHY，但 fuxi 的 regulator、时钟、复位、lane 配置尚未完整接入；缺任一项都会让 `/dev/block` 为空。
2. **真实电源和时钟**：当前最小 DTS 为 USB 探测服务，未宣称已经覆盖整机所有 RPMh 电源。需要对照厂商 fuxi DTS 逐节点补齐，并用日志验证 probe 顺序。
3. **调试通道稳定性**：USB 串口只是临时入口；若 USB 不通，需要保留 `earlycon`/pstore 或构造 header v4 后复用 Android 的调试通道。

### P2：进入图形和可交互系统前必须解决

1. **面板**：fuxi 使用三星 `m3 38 0c 0a`、1080×2400、DSC、command mode 面板，主线没有对应 panel driver。DPU/DSI 本身已有，缺的是面板初始化序列和板级 DSI 节点。
2. **触摸**：下游设备树确认是 ST FTS V521 SPI（`compatible = "st,spi"`，固件 `st_fts_m3.ftb`）；主线没有可直接匹配的 SPI 驱动/绑定，需移植并补齐 SPI、GPIO、中断、电源和固件加载。Goodix 器件是屏下指纹，不是触摸屏。
3. **GPU/WiFi**：Adreno 740 和 WCN7850 分别已有部分主线支持，但需要 fuxi 固件、PCIe/电源和校准数据，不能从 SoC 驱动存在推断真机可用。

### P3：长期功能缺口

蜂窝语音、音频 codec、相机 ISP/传感器、指纹、NFC、传感器和完整电量/充电管理都不属于当前启动闭环。它们应在 M1/M2 通过后单独立项，不能阻塞第一阶段的内核启动验证。

## 里程碑

| 阶段 | 验收标准 | 止损点 |
|---|---|---|
| M0 | 备份可校验，能用 `fastboot boot` 启动并回到 Android | ABL 拒绝临时启动时停止改镜像格式，先研究 v4 封装 |
| M1 | 主线 Image + fuxi DTB + initramfs 完成构建 | 配置无法解析时修正 `.config`，不碰设备分区 |
| M2 | USB 主机枚举 CDC ACM，看到 `FUXI_NATIVE_INIT_OK` | USB 失败就转早期日志/pstore，保留当前镜像 |
| M3 | UFS probe 成功并出现内部存储设备 | 缺电源/PHY 时回到厂商 DTS 对照，不刷写分区 |
| M4 | DRM/simpledrm 有稳定画面，随后接入 fuxi panel | 面板初始化失败时保留 framebuffer 探测目标 |
| M5 | 触摸、WiFi、GPU 基本可用 | 外设逐项验证，任何单项失败不回滚已验证链路 |

## 最近一次真机结果（2026-10-24）

已完成主线内核、fuxi DTB 和 initramfs 构建。对带压缩 ramdisk 的 v2 镜像以及独立 v4 镜像分别执行 `fastboot boot`，两次都得到 `Sending OKAY`，随后在 `Booting` 阶段 USB 断开并回到 fastboot。之后恢复活动槽为 `b` 并 `fastboot reboot`，Android 正常启动。

因此，ABL 接受自定义镜像已经确认；当前阻塞收敛为内核 handoff 后的早期启动问题，优先检查 DTB 装载地址、内存保留区、fuxi 内存节点和早期日志通道。详细输出见 `reports/native-boot-test-20261024.txt`。

## 安全边界

- 优先 `fastboot boot`，不直接刷写测试内核。
- 不擦写 `persist`、`modemst1/2`、`fsg`、`fsc`。
- 不回锁 bootloader，不刷低于当前版本的固件。
- 每次设备操作前确认当前槽位和备份校验；失败后只回 bootloader 重启。

详细驱动矩阵见 `research/01-mainline-drivers.md`，启动链风险见 `research/02-boot-and-hybris.md`。历史材料保留在 `archive/`，不作为当前路线入口。

## 11. 2026-10-25 凌晨实测记录：UEFI 装载链路打通，内核早期 panic

### 11.1 已打通（全部真机验证）

| 环节 | 证据 |
|---|---|
| ABL `fastboot boot` 接受自制镜像 | `Sending OKAY / Booting OKAY` |
| edk2 UEFI（GCC5 + DEBUG）可启动 | 进入 SimpleInit GUI / Shell |
| **手工 PE 装载内核**（绕过 EDK2 LoadImage 的 `Unsupported`） | 打印 `machine=0xaa64 EntryRVA=0x640B0 SizeOfImage=0xB90000` |
| FFS `ReadFile` 的 **4 字节前缀** | 内核头 `04 E2 B1 19 4D 5A`；DTB 头 `xx xx xx xx D0 0D FE ED`，已自动对齐 |
| 内核 DTB 传给 EFI stub | `DT 表 0xA72BB018 magic=D0 0D FE ED` |
| 放宽 `ExitBootServices` 运行时对齐校验 | `runtime entry start unaligned (0x9F5F7000), relaxed.` |
| 内核 EFI stub 执行到最后阶段 | 出现 `SetUefiImageMemoryAttributes` 系列调用 |

### 11.2 关键踩坑（务必记住）

1. **每次启动尝试后 ABL 会拒绝后续 `fastboot boot`**（报 `Invalid Parameter` / `Load Error`），
   必须 `fastboot reboot bootloader` 才能再试。早期关于“镜像大小限制”的结论都是这个假象导致的误判。
2. **ABL legacy boot 不接受 v2 header 的 dtb 字段**（`Load Error`），DTB 只能从 `vendor_boot` 取。
3. **arm64 `Image` 在 `CONFIG_EFI_STUB=y` 时以 `MZ` 开头**，ABL 直启会把 PE 头当指令执行；
   直启必须关闭 `EFI`/`EFI_STUB`（关闭后 Image 以 `nop; b stext` 开头）。
4. **EDK2 `Fv->ReadFile` 返回的数据带 4 字节前缀**，内核与 DTB 都要做 magic 扫描对齐。
5. **EDK2 `LoadImage` 对无重定位段的 arm64 内核返回 `EFI_UNSUPPORTED`**，必须手工按 PE 段表装载。

### 11.3 当前卡点

两条路径最终都表现为「内核跳转后数秒内静默崩溃/复位」：

- UEFI 路径：`SetUefiImageMemoryAttributes` 之后无任何输出；
- ABL 直启路径（EFI 已关闭）：3 秒内回到 fastboot。

已排除：DTB 指针错误、DTB 保留内存缺失（已补 44 个 `no-map` 区）、EFI stub 问题、ExitBootServices 对齐问题、PE 头问题。

### 11.4 下一步方案（需专门的日志通道）

没有 UART，必须让内核把 panic 日志写进 **pstore/ramoops 固定内存**，再由 UEFI 调试固件读取该物理内存并显示。
所需改动：
1. DTB 增加固定 `ramoops` 保留区（`compatible = "ramoops"`，固定 `reg`）；
2. 内核打开 `CONFIG_PSTORE`、`CONFIG_PSTORE_RAM`、`CONFIG_PSTORE_CONSOLE`（`console-ramoops` 记录 printk）；
3. UEFI 启动器增加“导出指定物理内存为文本”的调试模式；
4. 崩溃后重启进入 UEFI 调试固件，读取并显示内核日志。

风险：复位后 DRAM 内容是否保留需要实测；若不保留，则退回到“USB gadget 串口”（需内核先能启动到 initramfs）。

## 12. 2026-10-25 01:00 收尾记录：帧缓冲打点机制

### 12.1 本轮新增（可用）

1. **内核帧缓冲打点**：`arch/arm64/kernel/fuxi_early.c`
   - 命令行参数 `fuxi.fb=0x<base>,<stride>,<height>,<width>,<bpp>`
   - `fuxi_mark(stage)` 在屏幕左上角画品红色 48×48 方块，stage 0–5
   - 打点位置：`paging_init` 后(0)、`start_kernel`(1)、`mm_core_init` 后(2)、`sched_init` 后(3)、
     `kernel_init`(4)、`run_init_process` 前(5)
2. **启动器传递帧缓冲信息**：`FuxiLinuxBoot.c` 查询 GOP，把 fb 地址/stride/分辨率拼进内核命令行，
   通过 `EFI_LOADED_IMAGE_PROTOCOL.LoadOptions` 传给内核 stub
3. **内核命令行改由启动器传递**：关闭 `CONFIG_CMDLINE_FORCE`，启用 `CMDLINE_FROM_BOOTLOADER`

### 12.2 本轮实测结果

- `LoadOptions` 传递成功：屏幕打印出完整 `cmdline=console=ttyGS0,... fuxi.fb=0x80000000,1000,2400,1000,32`
- **但屏幕上没有任何品红色块** → 内核在 `paging_init` 之前就死了，
  即卡点在 `setup_arch()` 的最早期（memblock 初始化 / DT 解析 / early_init_dt_scan 一带）

### 12.3 已排除的日志方案

| 方案 | 结论 |
|---|---|
| pstore + ramoops | ❌ 复位后 DDR 被重新初始化，读到 0 字节 |
| EFI earlycon (`CONFIG_EFI_EARLYCON`) | ❌ Kconfig 为 `depends on SERIAL_EARLYCON && !ARM`，arm64 不可用 |
| USB gadget 串口 | ❌ 内核未到 initramfs |
| UART | ❌ fuxi 未引出 |

### 12.4 下一步（按优先级）

1. **让启动器自己画一个色块**，验证 GOP 帧缓冲地址与直写方式是否有效
   （若启动器的块可见而内核块不可见，即可确认内核死在 paging_init 之前）
2. **把打点提前到 MMU 开启之前**：在 `arch/arm64/kernel/head.S` 里用恒等映射直接写帧缓冲
   （需要先把 fb 地址通过 DT `/chosen` 或固定地址传给汇编阶段）
3. **对比 vendor 内核的早期启动参数**：CPU 启动方式、PSCI 版本、`CONFIG_ARM64_ERRATUM_*`、
   `CONFIG_ARM64_PA_BITS`/`VA_BITS`、GIC 初始化顺序是否和 vendor 一致
4. 若仍无法突破，考虑 **引入 UART 硬件接入**（拆机测试点/USB-C SBU 调试配件），这是最稳的日志通道

## 13. 自编厂商内核（VT/fbcon/KEXEC）实验记录

### 13.1 关键结论：vermagic 必须与手机内核完全一致

- 手机运行内核：`5.15.211-g9d5787a9b37e`（vermagic 同此串）。

  `5.15.220-gf9ca2b71f672-dirty`，厂商模块（USB/显示/UFS）全部因版本不匹配拒绝加载。

  并给 `scripts/setlocalversion` 打补丁去掉 dirty 的 `+`，得到与厂商一致的

## 14. 自编厂商内核的关键突破（2026-10-25 傍晚）

### 14.1 从备份内核里提取到厂商原始配置

备份的 stock 内核镜像内嵌 IKCONFIG，可无损提取：

```bash
build/linux/scripts/extract-ikconfig backups/20261024-172623/boot_b.img的kernel部分 > config-stock
```

厂商实际用 **AOSP clang 22.0.2（r596125，含 PGO/BOLT/LTO）+ Full LTO + CFI** 构建。

### 14.2 模块 ABI 验证结论（决定模块能否加载）

| 配置 | 模块 CRC 不符数 |
|---|---|
| 早期 tinyconfig 类配置 | 400+ ❌ |
| stock 原始配置 + CFI + ThinLTO（本机 clang 22.1.8） | **0 ✅** |
| stock + VT/KEXEC | 11（仅 modem/adsp/minidump 等非关键模块） |

结论：**配置才是模块 ABAT 的关键**，本机 Ubuntu clang 22 可复刻；VT/KEXEC 会通过间接配置影响少量符号 CRC。

## 15. KEXEC 通道实测记录（2026-10-25 晚）

### 15.1 已打通的部分

- **自编厂商内核（stock 配置 + KEXEC）成功启动**，厂商模块（显示/USB/存储）能加载：
  - 现象：`/dev/ttyACM0` 出现、USB-NCM `enx020000001302` up、`http://192.168.77.2:8080/status.txt` 返回
  - 关键：stock 配置 + CFI + ThinLTO + 精确提交 9d5787a9b37e，并修补 4 个模块（arm_smmu / qcom_iommu_util / rproc_qcom_common / qcom-dload-mode）的 `__versions` CRC、去掉模块签名
- **kexec 加载与跳转执行**：在 initramfs 的 busybox root shell 里完成
  `kexec -l Image --dtb=... --command-line=...` → `kexec -e`，之后手机复位（HTTP boot_id 变化），说明已跳出原内核
- 静态 aarch64 kexec 已构建：`work/kbuild/kexec-static`（1.5MB，strip 后 841KB）

### 15.2 卡点

- kexec 跳转后主线内核的控制台日志没抓到：USB 断开/重枚举瞬间抓取端也断开，需要主机端 udev 监控（已写 `scripts/watch-acm.sh`，但仍存在多读者竞争、权限重置、shell 看门狗超时等问题）
- initramfs 自动 kexec（`init_boot_auto.img`）不稳定：有时能到 shell，有时启动即回 fastboot；shell 提示符 `~ #` 有时被大量 `>` 噪声淹没

### 15.3 参考手册（重要）

`work/android-mainline-port`（yzddmr6 的同型设备移植手册）关键条目：

- 主线 DTB 缺 `__symbols__` 时 ABL 叠加 dtbo 会**静默失败**，`fastboot boot` 仍返回 OKAY
- RAM 测试用 **header v2（kernel+ramdisk+DTB）**；持久启动必须三件套 + 自签 AVB
- `fastboot boot` 停 Fastboot 优先查 DTB 的 `msm-id`/`board-id`
- 早期 ramoops 要用厂商设备树里的固定保留区

fuxi 实测：v2 带 dtb 仍被 ABL 拒（Load Error），与手册中平板设备不同，需继续走 vendor_boot/kexec 路线。
